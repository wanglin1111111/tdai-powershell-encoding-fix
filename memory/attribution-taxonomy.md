# 失败归因分类法（本领域专用）

> 对应论文：VeriSkill — Stage 1「失败归因与过滤（Failure Attribution and Filtering）」。
> 论文核心主张：**只有「技能相关」的失败才应触发技能演化**；把「工具限制」或
> 「任务本身不可满足」误判为技能缺陷，会把演化推向错误方向。

## 为什么需要这张表

这个技能领域（Windows 非-ASCII HTTP 载荷的端到端 UTF-8）有一个极易被误归因的特征：
**最常见的失效——PowerShell 5.1 把中文替换成 `?`——根因是工具序列化能力限制，
而不是技能知识缺口**。如果盲目「见到失败就改技能」，会写出大量针对单一工具的
补丁，把示例级噪声固化进技能（VeriSkill 称之为 task-specific noise）。

因此每次遇到编码失效，先按下表归因，**只有 ④ 类才进入 lesson 抽象与验证闭环**。

## 四类归因（对照 VeriSkill）

| # | 类别 | 本领域表现 | 是否触发技能演化 |
|---|------|-----------|------------------|
| ① | **任务不可满足（Task unsatisfiability）** | 服务端明确拒收该负载：如网关只接受 `Content-Type: text/plain`，或字段长度上限。失效与编码无关。 | ❌ 不触发。这是任务/接口契约问题，归调用方。 |
| ② | **工具/求解器限制（Prover limitation）** | **PS5.1 的 `Invoke-RestMethod` 用 Windows-1252/GBK 序列化**，无法产生 UTF-8 字节。这是工具的固有能力限制，不是知识缺口。 | ❌ 不触发技能内容修改。技能的应对方式是「绕过」——提供 `scripts/Send-Utf8Request.ps1`（字节数组封装）或迁移到 Node/PS7。技能文本只负责**指出该限制并给绕过路径**，不应试图「教会 PS5.1 输出 UTF-8」。 |
| ③ | **技能不合规（Skill noncompliance）** | 技能已提供相关指导，但调用方没遵循。例如仍手写 `Invoke-RestMethod` 直发字符串、或忘记 `charset=utf-8`。 | ⚠️ 不改技能内容，但可能需要**强化触发性**（让技能更易被命中），或在 SKILL.md 强化「必须使用封装」的措辞。 |
| ④ | **技能知识缺口（Skill knowledge gap）** | 技能确实缺少某类可复用知识。例如：技能只覆盖中文，但用户遇到了 emoji（4 字节 UTF-8）失效；或技能没说明 `Content-Length` 必须按字节而非字符计算导致截断。 | ✅ **进入 Stage2**：抽象责任 → 写入 evolution 记忆 → 构造 corpus 用例 → 跑验证门槛准入。 |

## 归因检查清单（遇到编码失效时逐条排查）

按顺序问，命中即停：

1. **服务端是否返回了明确的协议错误（4xx/5xx + 编码无关原因）？**
   → 是 → **① 任务不可满足**。修接口契约，不要动技能。

2. **是否在 PowerShell 5.1 上用原生 `Invoke-RestMethod` 直发字符串？**
   → 是 → **② 工具限制**。换用 `scripts/Send-Utf8Request.ps1`，或迁 Node/PS7。
   先确认：用 `scripts/encoding-safe-http.mjs` 走同一网关，是否就正常？（若是，则铁证归因于客户端序列化。）

3. **是否已知道要用封装，但实际仍绕过封装手写请求？**
   → 是 → **③ 不合规**。整改调用方代码；必要时强化 SKILL.md 的触发措辞。

4. **是否换上封装后、在 mock-gateway 上 `verify.mjs` 仍能复现失效？**
   → 是 → **④ 知识缺口**。这是真正需要演化技能的信号。走 Stage2：
   - 提取「诊断签名」（定位 / 责任 / 失效机制，见 `skill-evolution.md`）
   - 在 `corpus.json` 加一条能稳定复现的用例
   - 跑 `verify.mjs`，直到该用例通过且不影响其它用例（语义保持），才准入。

## 反向验证（避免误归因）

每次归因为「② 工具限制」时，建议同时用 **坏客户端**（`verify.mjs` 的 latin1 路径）
对同一 corpus 跑一遍。若坏客户端在非-ASCII 用例上全部失败、而编码安全客户端全部
通过，则双向印证：

- bug 真实存在（不是偶发）
- 根因在客户端序列化（不是网关、不是任务不可满足）
- 技能的「绕过工具限制」策略有效

这正是 `verify.mjs` 第二段「反向归因」的设计依据，也是 VeriSkill
「failure attribution 作为可靠学习信号」的落地。
